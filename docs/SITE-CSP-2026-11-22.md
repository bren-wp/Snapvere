# Snapvere website CSP — 2026-11-22 (code-level hardening)

The static website serves a Content-Security-Policy in both `site/_headers`
and `netlify.toml`. Both copies must be identical. The CI gate
`python tools/check_site_csp.py` computes SHA-256 hashes over the exact
raw UTF-8 content of every inline `<script>` block on every HTML page.
It verifies the matching `script-src` hashes and rejects any unexpected
inline script or policy drift.

## Allowed resources

- External JavaScript: same origin plus `www.googletagmanager.com` only. The Google Analytics loader runs **only after user consent** and only if `gaId` is configured.
- Network connections: same origin, `www.google-analytics.com` and `region1.google-analytics.com` for consented GA4. The app does not use analytics.
- Images: same origin, data URI for local icons, and the two GA collection hosts (used only following consent).
- Fonts: same origin. Styles: same origin plus `'unsafe-inline'` for existing decorative `style=` attributes in the homepage's application mockups; **no JavaScript unsafe-inline**.
- Frames, workers, objects, framing by other sites and base URI injection are blocked; HTTP subresources are upgraded.

## Browser QA remaining

This is a static security regression, **not** proof of cross-browser behavior.
Before resolving Issue #47, run real browser tests on Chrome, Firefox, Edge,
Safari and a mobile viewport. Confirm homepage rendering, structured data
(JSON-LD), accept/decline/revoke flows using a configured test GA ID,
CSS/inline styling, download links, external release link, and production
response headers from the actual hosting CDN. Inspect CSP console violation
events; do not weaken the script policy to hide failures.

Any edit to inline JSON-LD or the initial `documentElement` bootstrap
requires updating **both** CSP strings with reviewed SHA-256 hashes.
CI must fail until this is done. This PR does not enable analytics.
