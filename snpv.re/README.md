# Snapvere sharing service

Run Node.js 24 behind an HTTPS reverse proxy for snpv.re. Keep site/ alongside snpv.re/ to share the original stylesheet, favicon and font. Set SNAPVERE_SHARE_STORAGE to a private directory outside the repository (0700) and SNAPVERE_SHARE_KEY to a random secret of at least 32 bytes. Start with node snpv.re/server.mjs. Create a one-hour, single-use upload code with node snpv.re/server.mjs grant. Never distribute the signing key to clients.

POST /api/v1/shares with Bearer upload code, Content-Type, Content-Length and X-Share-TTL (3600, 86400 or 604800). Body is raw media, maximum 16 MiB technical limit. Requests stream into exclusive staging files, with exact byte-count validation, a SHA-256 digest and disk sync before publication. The metadata endpoint exposes the SHA-256 digest for new shares. Signature checks are not complete media decoding. Set SNAPVERE_SHARE_QUOTA_BYTES to a positive integer (default 2147483648); admission accounts for existing files, conservatively reserves in-flight uploads and keeps at least 64 MiB free. Failed validation and replay remove their own staging files before returning; admission retries transient directory disappearance during concurrent cleanup. Media reads reject leaf links and compare the opened handle to the inspected identity. These checks do not constitute protection against an administrator or a hostile process with write access to the private storage directory. Use one service process per storage directory and an independent filesystem quota; the application-level limit is not a hard multi-process quota. Response includes canonical HTTPS link, expiry and separate revocation secret. DELETE /api/v1/shares/TOKEN with Bearer revocation secret. Recipients need only the secret URL. No public media list. Revocation does not recall existing downloads or active streams. The desktop dialog now supports explicit revocation while its result is open and cancelling the current upload. POST /api/v1/shares/recover with the original, still-valid Bearer upload code and no body recovers a previously committed link and revocation secret without sending media again. New share capabilities are derived via domain-separated HMAC-SHA256; only hashes are persisted. Treat the upload code as sensitive until it expires. Recovery fails for revoked, expired, missing or pre-recovery-version shares. Key rotation invalidates outstanding grants and recovery; existing published URLs remain usable. A crash after consuming the code but before publication remains fail-closed and requires a new code. No desktop secret persistence is added. Cancellation does not guarantee rollback after server acceptance; keep the expiry short for sensitive content.

Before public deployment: configure TLS, hostname validation, no private URL or credential logging, proxy rate/body limits, disk quotas, scheduled expiry cleanup, backups, abuse reporting, full media validation and physical/native acceptance. Current media checks validate signatures, not complete decodes. Expired data remains stored until cleanup. Run `node snpv.re/server.mjs purge-expired` using the same private environment during a maintenance window with uploads stopped. The command removes only recognized expired copies with consistent metadata and media size, and reports preserved malformed records. It does not remove local desktop originals or unknown files. Configure a scheduler, disk quotas and an operator review of preserved records before production use. Password protection and account-based provisioning are not implemented. No service is represented as live.
